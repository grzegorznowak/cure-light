+Sequence over the state's designated, pinned source bytes (captured verbatim from bytes — no `gh --jq` shells, no trim/newline normalisation):
+
+1. **`claims_prepare`** captures every authorized source into one run dir (`{run_dir, sources[]}` locally, `{review_target, run_dir, resources[]}` for remote intake) and frames it once: one `capture-manifest/1` (`captures_sha256`; per source byte identity `sha256`, `byte_length`, spans, plus the plugin's `blob_algorithm: git-blob-sha256` and `blob_oid`) and `slices/manifest.json` + payloads (`slice_id=sha256:…`). The whole source is labeled in one piece when it is within the full-label caps (≤16 KiB raw bytes, ≤80 units, ≤64 KiB complete serialized worker input); otherwise bounded byte-exact worker payloads are written: ≤16 KiB raw text / ≤80 units / ≤64 KiB serialized input per slice, ≤4 preceding overlap units for seam audits, ≤32 slices by default; overlap-only slices are forbidden, and an oversized indivisible unit fails the run (never split). Raising the slice budget is an explicit recorded decision that changes the slice recipe/IDs — never a silent cap increase. The repo-side blob OID is pinned independently (§Pin immutable source blocks).
+2. **Labeling children** (fleet-spawned; coordinator fallback per the stated budget) return only proposals: `claim-proposals/1` for whole-source labeling, or one `slice-proposals/1` per slice — primary assignments over core non-separators only, one audit vote per overlap non-separator, one grouping vote per visible non-separator adjacency pair, and the slice's left/right boundary declaration. Children never run the tools and never compute IDs/hashes; their instructions are the plugin's **bundled slice instructions** returned by `claims_prepare` (`claim-registry-slice-instructions/1`). Those bundled instructions are the run's operational worker contract; the coordinator may inspect the bundle implementation for **diagnosis only**, never as an undisclosed substitute instruction set. If the published instructions are insufficient to produce validator-valid proposals, **stop Phase 0 and report a substrate defect to the plugin maintainers** — the run never invents the missing rules.
+3. **`claims_finalize`** merges the children deterministically and seals the run: a differing audit rationale is retained as a warning; a state/subtype/role/grouping disagreement is a hard failure (`proposal-reconciliation/1`). A failed reconciliation publishes a failure report and never a usable merged artifact; the merged file is removed on failure so a stale success cannot be consumed. It produces the canonical `claim-registry/1` registry, the validation report, and a sliced run's `claim-run-manifest/2` sealed with the mandatory `labeling` block (frame-slices manifest, every child, merged proposals, reconciliation report) and never representable as `/1`. **Worker proposals are the run's recorded evidence, not a draft.** The coordinator never overwrites, repairs or normalizes a worker-authored proposal into the authoritative submitted file: `gate_check` replays the submitted bytes, so a rewritten proposal would silently become the sealed record in place of the worker's own output. On invalid worker output, retain the original file, diagnose the rule, and obtain a **new worker-authored** proposal under the documented instructions (where labeling runs in coordinator-fallback mode, the coordinator fills the worker role and authors the proposal as such) — retaining both attempts — and if the contract remains unclear or finalize still fails, stop Phase 0 and escalate. Any coordinator-side transport/format repair requires a separately approved, narrowly defined provenance protocol; it is never implied by this step.
+4. **`gate_check`** (`{run_manifest_path, require_sliced:true}`; `require_sliced:false` for a full-label run): `status=verified` **and both coverage booleans** (`finalized_unclaimed`, `complete_registry_claims`) is the only authority to treat the registry as complete. On `/2` the gate replays the labeling block — span identity against captured bytes, recipe partition/payload bytes, deterministic reconciliation, and reconciled ownership/grouping/rationales against the registry.
+5. **Project** the claims/coverage pages from the canonical registry — identical claim IDs, counts and `registry_hash`; the pages are queryable views, never a substitute, and window/slice IDs never become claim IDs (notebook-plan-contract.md).
